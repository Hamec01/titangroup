# TITANOR GROUP — ПРАВИЛА ДЛЯ АГЕНТА

**Для:** Cursor / Codex и других агентов.
**Цель:** делать проект маленькими проверяемыми шагами, экономить токены и сохранять контроль владельца.

## 1. Что прочитать перед работой

```text
PROJECT_VISION.md
PROJECT_ROADMAP.md
AGENT_RULES.md
TITANORGROUP_VPS_MIGRATION_AGENT_TZ.md
```

Агент не должен молча заменять этот план своим.

## 2. Главное правило

```text
одна задача
→ одна функция
→ минимум файлов
→ одна проверка
→ один коммит
```

Нельзя параллельно переделывать соседние части «для красоты».

## 3. Размер задачи

Одна задача должна иметь один проверяемый результат.

Хорошо:

```text
Добавить GET /api/health.
Не менять Docker, форму и другие API.
Запустить TypeScript и build.
```

Плохо:

```text
Сделай весь Titanor Time и улучши всё, что увидишь.
```

Если задача большая, сначала разбить её и остановиться.

## 4. До изменения

Коротко написать:

```text
Цель:
Ожидаемые файлы:
Проверка:
Риски:
```

Без длинного пересказа проекта.

## 5. После изменения

Минимальный ответ:

```text
Готово.
Изменены: <файлы>
Проверки: <результат>
Не сделано: <если есть>
Следующий шаг: <одна строка>
```

Полный diff не вставлять. Владелец смотрит его сам.

## 6. Команды владельца

```bash
git status --short
git diff --name-only
git diff --stat
git diff
git log --oneline --decorate -10
npx tsc --noEmit
npm run build
```

Для Docker:

```bash
docker compose config
docker compose ps
docker compose logs --tail=100
```

## 7. Коммиты

Одна задача — один коммит.

Формат:

```text
type(scope): short description
```

Примеры:

```text
feat(health): add application health endpoint
chore(docker): add standalone production image
refactor(storage): move service content to local json
feat(time): add employee worksite assignments
fix(auth): block inactive users
```

Перед коммитом:

```bash
git diff --check
npx tsc --noEmit
```

Для runtime-задач также:

```bash
npm run build
```

Не делать merge в `main`, force push или удаление ветки без разрешения.

## 8. Запрет на лишние изменения

Без отдельной задачи нельзя:

- менять весь дизайн;
- переименовывать много файлов;
- обновлять все зависимости;
- менять ORM;
- менять базу;
- заменять Caddy;
- менять Docker-архитектуру;
- добавлять новые сервисы;
- удалять рабочий код до проверки замены;
- форматировать весь репозиторий;
- менять URL;
- добавлять новые функции вне задачи.

Проблему можно описать отдельно, но не чинить молча.

## 9. Production-безопасность

Без подтверждения запрещено:

- останавливать CollabStudio;
- менять его контейнеры, базу, сеть или secrets;
- использовать порт `3000` для Titanor;
- выполнять `docker system prune`;
- выполнять `docker volume prune`;
- выполнять `docker network prune`;
- перезапускать Docker daemon;
- перезагружать сервер;
- менять существующие Caddy-блоки CollabStudio;
- менять MX, SPF, DKIM, DMARC и Zoho verification;
- переключать production DNS;
- удалять Vercel или Supabase;
- удалять production volumes;
- публиковать базу наружу.

Полные запреты находятся в большом ТЗ миграции.

## 10. Секреты

Никогда не коммитить:

- `.env`;
- пароли;
- API secrets;
- SMTP password;
- Supabase Service Role Key;
- Cloudinary API Secret;
- private keys;
- cookies и токены.

Разрешён только `.env.example` без значений.

Секреты нельзя выводить в отчётах и логах.

## 11. База Titanor Time

Она должна быть отдельной от CollabStudio.

Запрещено:

- использовать PostgreSQL CollabStudio;
- использовать его volume или network;
- делать destructive migration без backup;
- удалять таблицы без подтверждения.

До создания схемы агент показывает:

```text
Сущности
Поля
Связи
Ограничения
Индексы
Правила удаления
```

Только после утверждения создаётся migration.

## 12. Роли и права

Скрыть кнопку недостаточно. Каждое действие проверяется на сервере.

Обязательно проверить:

- работник не видит чужие часы;
- прораб не видит чужой объект;
- пользователь не повышает себе роль;
- отключённый аккаунт не работает;
- подтверждённые часы не меняются обычным update;
- admin API защищён.

## 13. Правила для часов

- часы валидируются на сервере;
- дата валидируется на сервере;
- объект должен быть назначен работнику;
- нельзя писать от имени другого пользователя;
- конфликтующие записи обрабатываются по утверждённым правилам;
- изменение статуса фиксируется;
- возврат содержит причину;
- подтверждение содержит reviewer и timestamp;
- важные изменения попадают в audit log.

## 14. Проверки

### TypeScript

```bash
npx tsc --noEmit
```

### Runtime или страница

```bash
npm run build
```

### Docker

```bash
docker compose config
docker compose build
```

### API

Проверить:

- успешный запрос;
- невалидные данные;
- отсутствие авторизации;
- неправильную роль.

### База

Проверить:

- migration применяется;
- новая база поднимается;
- данные переживают restart;
- есть backup/rollback.

## 15. Контрольные точки

Остановиться перед:

- изменением production secrets;
- первой migration production-базы;
- первым запуском контейнера;
- изменением Caddy;
- созданием preview DNS;
- изменением основного DNS;
- merge в `main`;
- удалением Supabase;
- отключением Vercel;
- запуском на реальных работниках.

Формат:

```text
CHECKPOINT:
Что готово:
Что будет изменено:
Как проверить:
Как откатить:
Нужно подтверждение владельца.
```

## 16. Ошибки

Если проверка не прошла:

1. остановиться;
2. показать ошибку;
3. объяснить вероятную причину;
4. предложить минимальное исправление;
5. повторить ту же проверку.

Без разрешения запрещено:

```bash
npm install --force
npm audit fix --force
git reset --hard
git push --force
chmod -R 777
```

## 17. Экономия токенов

Агент должен:

- не пересказывать весь проект;
- не вставлять полный код изменённых файлов;
- не выводить полный diff;
- не повторять согласованные правила;
- читать только нужные файлы;
- использовать поиск по коду;
- менять минимальный участок;
- не писать длинную документацию к микрошагу.

Длинный отчёт нужен только после крупного этапа, перед production или при серьёзной ошибке.

## 18. Шаблон маленькой задачи

```text
ЗАДАЧА:
[один конкретный результат]

КОНТЕКСТ:
[только нужная информация]

РАЗРЕШЕНО:
[точные файлы или область]

ЗАПРЕЩЕНО:
[что нельзя трогать]

КРИТЕРИИ ГОТОВНОСТИ:
[проверяемый результат]

ПРОВЕРКИ:
[точные команды]

ПОСЛЕ ВЫПОЛНЕНИЯ:
Коротко перечислить изменённые файлы и результат проверок.
Не вставлять полный diff.
Не начинать следующий шаг.
```

## 19. Когда задача завершена

- сделан один понятный результат;
- не затронуто лишнее;
- diff просмотрен;
- проверки прошли;
- секретов нет;
- создан один коммит;
- предыдущая функция работает;
- следующий этап не начат самовольно.

## 20. Главное

Задача агента — не изменить как можно больше, а сделать один шаг так, чтобы владелец:

- понял изменение;
- посмотрел diff;
- проверил результат;
- смог откатить;
- не зависел от одного агента.
