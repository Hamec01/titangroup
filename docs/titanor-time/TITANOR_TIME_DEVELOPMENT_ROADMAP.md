## ТЕКУЩЕЕ СОСТОЯНИЕ

Публичный сайт Titanor Group уже работает в production:

- домен: https://titanorgroup.fi
- развёрнут на личном VPS;
- работает в отдельном Docker-контейнере;
- публичный сайт использует host port 3100 → container port 3000;
- перед контейнером работает Caddy;
- healthcheck: /api/health;
- административный портал публичного сайта: /ship-admin-portal;
- изображения сохраняются локально через volume;
- Cloudinary и Supabase больше не являются частью целевой архитектуры;
- почта Zoho Mail и существующие DNS-записи не должны быть затронуты;
- публичный сайт нельзя ломать, переносить или перестраивать без необходимости.

Titanor Time должен стать отдельным внутренним приложением:

- предполагаемый домен: app.titanorgroup.fi;
- preview-среда: app-preview.titanorgroup.fi;
- отдельный контейнер;
- предполагаемый локальный адрес production-контейнера: 127.0.0.1:3200;
- отдельный PostgreSQL;
- база данных не публикуется наружу;
- отдельные переменные окружения;
- отдельный healthcheck;
- отдельные логи;
- отдельный backup;
- обновление Titanor Time не должно перезапускать публичный сайт.

## ПОРЯДОК РАЗРАБОТКИ

Принята следующая последовательность:

1. Технический фундамент.
2. Минимальный административный контур.
3. Первый рабочий кабинет сотрудника.
4. Контур прораба.
5. Финальное утверждение администратором.
6. Экспорт и пилот.
7. GPS, полноценный offline-first и расширенная PWA-функциональность.

**Owner priority override, 2026-08-05:** клиент утвердил Attendance Clock как основной ежедневный
worker-flow. После activation/onboarding и базового E2E GPS snapshots + offline Check In/Check Out
перенесены в обязательный ЭТАП 7A перед отчётами и пилотом; полный scope — `PROJECT_ROADMAP.md`.
Остальные offline-мутации и push по-прежнему остаются поздней расширенной PWA-функциональностью.

Начинаем с администратора, но НЕ создаём сначала всю административную панель.

Первый вертикальный сценарий:

1. Администратор входит в приложение.
2. Создаёт город или производственную площадку, если это требуется моделью.
3. Создаёт объект.
4. Создаёт рабочую область объекта.
5. Создаёт рабочий шаблон.
6. Регистрирует работника.
7. Назначает работника на объект.
8. Назначает рабочий шаблон.
9. Открывает расчётный период.
10. Создаёт или выдаёт код активации.
11. Работник активирует учётную запись.
12. Работник входит в приложение.
13. Работник видит правильный объект, рабочую область, шаблон и текущий период.

Первый контрольный результат должен подтверждать цепочку:

администратор создал объект
→ зарегистрировал работника
→ назначил его
→ работник активировал аккаунт
→ вошёл
→ увидел своё назначение

Не начинай работу с декоративного dashboard, наполненного фиктивной статистикой.

Учти следующие обязательные правила:

- рабочий отрезок может переходить через полночь;

- отображение выполняется в Europe/Helsinki;

- прораб может иметь временного заместителя;
- рабочий день имеет тип;
- перерыв может быть отдельной сущностью;

- исправление создаёт новую корректирующую версию;
- аудит append-only;
- денежные расчёты и окончательные правила TES не зашиваются преждевременно.

## ТЕХНИЧЕСКИЕ ПРИНЦИПЫ

Следуй реальному технологическому стеку репозитория. Не придумывай замену существующему стеку без необходимости.

Если проект использует Next.js App Router, Prisma, TypeScript, Docker и PostgreSQL, проектируй решения в соответствии с ними.

Если обнаружишь другой стек:

- зафиксируй фактическое состояние;
- объясни расхождение;
- адаптируй документы;
- не выполняй масштабную миграцию без отдельного решения.

Обязательно учитывай:

- strict TypeScript;
- server-side authorization;
- пароли только в виде безопасного hash;
- обязательную 2FA для администраторов как архитектурное требование, даже если она будет реализована отдельным этапом;
- CSRF-защиту в зависимости от механизма сессий;
- secure, httpOnly, sameSite cookies;
- rate limiting для входа и активации;
- защиту от enumeration пользователей;
- audit log;
- request ID;
- structured logging;
- отсутствие координат GPS в обычных логах;
- минимизацию персональных данных;
- FI/EN/RU;
- timezone Europe/Helsinki;
- accessibility;
- mobile-first для работника;
- desktop-first для администратора и прораба;
- touch targets не меньше 48 px;
- отсутствие зависимости только от цвета или hover.

GPS и offline-first не входили в первоначальный implementation slice. Позднее owner-approved
Attendance Clock выделен в ЭТАП 7A (`PROJECT_ROADMAP.md`): это точечное исключение только для
Check In/Check Out. Push-уведомления и общий offline-first остальных мутаций остаются вне этого
среза; архитектура не должна блокировать их последующее добавление.

## ПРОВЕРКА

После создания документов выполни самопроверку:

1. Все внутренние ссылки работают.
2. Mermaid-блоки синтаксически корректны.
3. Route names совпадают между screen map и permission matrix.
4. Названия сущностей совпадают между ERD и API.
5. Permissions совпадают между матрицей и endpoint.
6. Статусы табеля определены в одном месте и не противоречат друг другу.
7. Первый end-to-end сценарий полностью покрывается экранами, данными и API.
8. Не осталось зависимости от Supabase или Cloudinary.
9. Предлагаемая архитектура не затрагивает работающий публичный сайт.
10. Документы не содержат секретов или production credentials.
