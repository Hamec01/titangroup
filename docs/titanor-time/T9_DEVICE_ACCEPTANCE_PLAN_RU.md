# Titanor Time — T9.7: проверка на реальном телефоне

```text
Статус: 🟡 подготовлено, ручная проверка владельцем ещё не выполнена
Дата подготовки: 2026-08-20 Europe/Helsinki
Среда: отдельная pilot/preview-среда с HTTPS, не production
Участники: владелец в роли ADMIN + один новый тестовый WORKER на реальном телефоне
```

## 1. Что доказывает T9.7

Это не повтор Playwright-эмуляции. Владелец приложения проходит реальный процесс:

```text
ADMIN создаёт объект/работника/назначение
→ выдаёт одноразовую ссылку активации
→ WORKER активирует аккаунт на телефоне
→ устанавливает PWA
→ выполняет GPS Check In/Out и offline-сценарий
→ заполняет и отправляет timetable
→ ADMIN без участия FOREMAN проверяет и финально утверждает табель
```

Закрыть T9.7 можно только фактическими результатами с физического устройства. Эмуляторные тесты
T8 уже зелёные, но не заменяют этот gate.

## 2. Обязательный Gate 0 — безопасный адрес

Телефон должен открывать **актуальную pilot-сборку по HTTPS**. Обычный адрес вида
`http://84.247.130.242:3244` не подходит: preview слушает только loopback, а Service Worker/PWA
на обычном HTTP IP не имеет secure context.

До начала проверки должны быть подтверждены:

- отдельный временный HTTPS hostname;
- hostname ведёт только на pilot app, не на production;
- pilot использует отдельную тестовую БД;
- `/api/health` и `/api/ready` возвращают `200`;
- открывается именно commit, предназначенный для T9.7;
- production container/image/database не изменены;
- после проверки hostname и disposable-ресурсы можно удалить.

Activation link является одноразовым секретом. Его можно передать тестовому работнику лично или в
закрытом сообщении, но нельзя публиковать в отчёте, скриншоте или общем чате.

## 4. Подготовка ADMIN

Использовать отдельные понятные имена с префиксом `PILOT`, чтобы данные потом легко найти и
отделить от настоящих:

1. Войти как `ADMIN` или `SUPER_ADMIN` на компьютере.
2. Создать `PILOT`-объект рядом с фактическим местом телефона.
3. Создать рабочую зону (`Work area`).
4. Настроить геозону на реальные координаты места проверки; для первого прохода использовать
   практичный радиус, например 150–250 метров.
5. Создать или выбрать шаблон рабочей недели.
6. Создать нового `PILOT`-работника с уникальным employee number.
7. Создать действующее с сегодняшней даты primary assignment на pilot-объект.
8. Убедиться, что для сегодняшней даты существует `OPEN` period. Создание assignment внутри уже
   открытого периода автоматически добавляет participant/timesheet/draft, поэтому закрывать
   существующий период только ради теста не требуется.
9. Открыть карточку работника и нажать `Issue activation code`.
10. Передать работнику `Copy activation link` или показать QR лично.

Ожидается: кнопка активации доступна, отображаются code/QR/expiry, а worker ещё не считается
активированным до использования ссылки.

## 5. Активация WORKER на телефоне

1. Открыть activation link на телефоне.
2. Проверить показанное имя работника.
3. Нажать `Continue`.
4. Задать новый пароль длиной минимум 8 символов.
5. После активации убедиться, что приложение автоматически открыло `/worker`.
6. Закрыть браузер, открыть снова и убедиться, что сессия сохранилась.

Не передавать пароль обратно ADMIN или разработчику. Для диагностики достаточно username,
времени и точного текста ошибки.

## 6. Установка PWA

Открыть `/worker/install` из ссылки `Install app`.

### Android / Chrome

1. Нажать `Install Titanor Time`, если кнопка показана.
2. Если кнопки нет — меню Chrome → `Install app` или `Add to Home screen`.
3. Запустить Titanor Time с иконки на домашнем экране.

### iPhone / Safari

1. Нажать `Share`.
2. Выбрать `Add to Home Screen`.
3. Подтвердить `Add`.
4. Запустить Titanor Time с новой иконки.

Проверить в обоих случаях:

- иконка Titanor Time отображается корректно;
- приложение открывается без адресной строки в standalone-режиме;
- стартовая страница — `/worker`;
- авторизация сохранилась;
- нет белого экрана или бесконечного `Checking install options…`.

## 7. Реальный GPS и online clock

Сначала выполнять действия в установленной PWA при включённой сети и Location permission:

1. Проверить, что pilot-объект доступен для выбора.
2. Выполнить `Check In` внутри геозоны.
3. Убедиться, что UI показывает `Clocked in`, правильный объект и работающий timer.
4. Полностью закрыть и снова открыть PWA — открытая смена должна сохраниться.
5. Выполнить `Check Out`.
6. Убедиться, что UI вернулся в `Clocked out`.

Дополнительный отрицательный GPS-тест выполняется только если ADMIN заранее создал второй
назначенный объект с геозоной заведомо далеко от телефона: попытка `Check In` должна показать
`OUTSIDE_GEOFENCE` и не открыть смену. Не уменьшать реальную геозону до абсурдного радиуса ради
получения ошибки.

## 8. Offline и настоящий cold restart

1. При включённой сети открыть `/worker` и дождаться полной загрузки.
2. Отключить Wi-Fi и mobile data, сохранив Location permission.
3. Выполнить offline `Check In`.
4. Полностью выгрузить PWA из списка последних приложений.
5. Снова открыть PWA с иконки, всё ещё без сети.
6. Убедиться, что offline shell показывает сохранённое состояние, а не browser error.
7. Выполнить offline `Check Out`.
8. Включить сеть.
9. Нажать `Sync now`, если автоматическая синхронизация ещё не завершилась.
10. Дождаться отсутствия pending/terminal ошибок и обновления authoritative clock state.
11. Ещё раз полностью закрыть/открыть PWA и проверить `Clocked out`.

Ожидается: одна закрытая смена, без двойных событий и без потери одной половины. При неизвестном
результате не нажимать многократно; записать точное время и текст, чтобы разработчик проверил
durable outbox/receipt в БД.

## 9. Timetable на телефоне

1. Открыть `My periods`.
2. Открыть текущий период и `View or edit hours`.
3. Открыть сегодняшний день.
4. Проверить, что записанная смена видна.
5. Добавить или изменить один интервал. Если меняется recorded Check In/Out, указать обязательную
   понятную причину.
6. Сохранить и перезагрузить страницу.
7. Проверить итоговые часы и отсутствие горизонтального overflow.
8. Открыть `Submit timesheet`, проверить summary и отправить табель.

После отправки табель должен стать read-only, а старая/новая информация не должна исчезнуть после
перезапуска PWA.

## 10. ADMIN утверждает без FOREMAN

FOREMAN для pilot-объекта не назначается.

1. ADMIN открывает `Timesheets` и находит отправленный табель.
2. В `Review` проверяет SITE/NON_SITE scopes.
3. Подтверждает необходимые scopes как ADMIN.
4. Выполняет final approval.
5. Проверяет статус `FINAL_APPROVED`.
6. Открывает отчёт `By worker` и убеждается, что часы присутствуют.

Отсутствие FOREMAN не должно создавать blocker. Техническое состояние `FOREMAN_APPROVED` означает
«review завершён», а не обязательную подпись прораба.

## 11. Security/logout smoke

1. Выполнить logout в PWA/браузере, если действие доступно в текущем UI.
2. Повторно открыть `/worker` — персональные страницы не должны открываться как авторизованные.
3. Не входя WORKER, попробовать открыть ADMIN URL — доступ должен быть отклонён.
4. После повторного входа убедиться, что собственные данные работника доступны, а чужие — нет.

Текущая account-bound offline защита не должна показывать snapshots другого пользователя. Нельзя
очищать IndexedDB вручную до фиксации возможной ошибки — это уничтожит диагностические данные.

## 12. Как сообщать результат

Для каждого раздела прислать `PASS` или `FAIL`:

```text
Устройство/ОС/браузер:
4 ADMIN setup: PASS/FAIL
5 Активация: PASS/FAIL
6 PWA install: PASS/FAIL
7 GPS online: PASS/FAIL
8 Offline cold restart: PASS/FAIL
9 Timetable/submit: PASS/FAIL
10 ADMIN approval без FOREMAN: PASS/FAIL
11 Security/logout: PASS/FAIL
```

Для `FAIL` обязательно добавить:

```text
время Europe/Helsinki
роль
адрес страницы
что нажали
что ожидали
что произошло
точный текст ошибки
скриншот без пароля, activation token, cookie и сырых GPS-координат
```

После каждого FAIL тест останавливается на первой сломанной границе. Разработчик сначала проверяет
browser → API → DB и исправляет подтверждённый дефект отдельным коммитом; затем повторяется
исходный шаг и соседний сценарий.

## 13. Критерий завершения T9.7

- минимум один реальный телефон проходит §§4–11;
- для проверенной платформы зафиксированы модель, ОС и браузер;
- activation, install, GPS, offline cold restart, sync, timetable и admin approval подтверждены;
- все найденные дефекты исправлены и перепроверены;
- Android и iPhone отмечены раздельно: непроверенную платформу нельзя объявлять PASS;
- временная HTTPS/pilot-среда удалена только после сохранения evidence;
- production не менялся в ходе acceptance.
