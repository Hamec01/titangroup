## 1. Что делает переключатель (после правки F03)

Поле `WorkSite.gpsOftenUnavailable` (в схеме с T14 — **миграция не нужна**). Значение переключателя
изменено: теперь оно **только пояснительное**.

Когда включено для объекта:
- **администратор** в карточке проблемы учёта (`/admin/review → запись`) видит заметку: «Объект
  отмечен как место, где часто нет GPS-сигнала… отметку без координат обычно можно принять…
  автоматически ничего не принято»;
- **работник** на экране отметки видит спокойную строку: «На этом объекте часто нет GPS-сигнала.
  Если телефон не определит местоположение — это нормально: отметка всё равно сохранится, и её
  проверит администратор».

**Что переключатель НЕ делает:**
- **не** закрывает исключения автоматически (отметки без координат по-прежнему идут в `/admin/review`);
- **не** меняет старые записи (флаг читается только при создании новой отметки, задним числом
  ничего);
- не трогает `LOW_ACCURACY`, `OUTSIDE_GEOFENCE_*`, часы, геозоны.

Автоматическое принятие таких отметок — **отдельный будущий шаг**, `R15_MEYER_GPS_AUTOACCEPT_PLAN_RU.md`,
включается только по отдельному решению.

## 3. Как применить (после подтверждения владельца) — два равнозначных пути

### Путь A — админ-UI (предпочтительно)
1. Войти под `oleksandr` (SUPER_ADMIN) или `yurii` (ADMIN).
2. `Настройки → Объекты → Meyer Turku Shipyard → Редактировать`.
3. Поставить галочку **«На объекте часто нет GPS-сигнала (корпуса судов, крытые цеха)»**.
4. Сохранить. → `PATCH /api/admin/sites/b38b9b64-…` `{version:3, gpsOftenUnavailable:true}` →
   поле записано, `version` → 4, audit `SITE_UPDATED`. **Обычное админ-действие, не деплой.**

### Путь B — psql (если браузерной сессии нет)
```
docker exec -i titanor-time-prod-db psql -U titanor_time_prod -d titanor_time \
  -v ON_ERROR_STOP=1 -v actor=ab393eb7-1db2-44fd-98b4-cde3593370f1 \
  < ops/titanor-time/r15-d7/meyer-gps-often-unavailable.sql
```
(`ab393eb7…` = `oleksandr`, ACTIVE SUPER_ADMIN. Или `77b75c72-4676-4f4e-bd38-4faeb3b413d2` =
`yurii`, ACTIVE ADMIN.) Одна транзакция: PRECHECK (актор активен и SUPER_ADMIN/ADMIN; строка =
Meyer, флаг `false`, version 3, не finished) → UPDATE + `SITE_UPDATED` audit (та же форма
`afterValue`, что у роута) → POSTCHECK (флаг `true`, version 4, ровно 1 свежий audit, ровно 1
объект с флагом на prod) → COMMIT. Любое несоответствие → RAISE EXCEPTION → ROLLBACK.

**Протестирован на disposable schema-100 БД:** нормальный путь коммитит (флаг `false→true`, version
`3→4`, 1 audit, другие объекты не тронуты); без `-v actor` / деактивированный актор / кривой uuid /
повторный запуск — все прерываются, ничего не записано.

Оба пути дают идентичный результат (поле + `version+1` + один `SITE_UPDATED` audit).
