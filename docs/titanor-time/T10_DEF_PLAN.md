### Исходный план D


**Проблема (баг).** В Финляндии смена 07:00–15:30 = **8 оплачиваемых часов**, не 8:30 — обед 30 мин
неоплачиваемый. Модель перерывов есть (`BreakSegment.paid`, `worked = gross − unpaid breaks`), но
автоматически ничего не вычитается: если работник не отметил перерыв сам, смена считается целиком.
В PDF-экспорте видно `Unpaid brk 0 h 0 min` и полные часы → путаница с бухгалтерией.

**Решения владельца:**
- Автоматом. «8:30 = 8 часов почти везде и всегда».
- Источник 30 минут — **плановый перерыв шаблона** (`WorkScheduleTemplateVersionDay.plannedBreakMinutes`
  / `TimesheetPlannedShift.plannedBreakMinutes`; поле в UI шаблона уже есть, сейчас у пилота стоит 30).
- Вычет **после закрытия рабочего дня** (Check Out) — часы показываются уже минус 30 мин, везде
  консистентно (дашборд, отчёты, экспорт).
- **Без двойного вычета**: если работник сам отметил перерыв — используем его, авто-30 не добавляем.
- Оставить **галочку «обед оплачивается»** (на шаблон/объект) — для заказчиков, кто оплачивает обед.

**Предлагаемая реализация (обратимая, без миграции данных):**
- Ядро `lib/reporting/worked-time.ts` — единая формула, её переиспользуют дашборд, все отчёты,
  экспорт, блокировка периода. Добавить **`effectiveUnpaidBreak`** на уровне ДНЯ:
  `recordedUnpaid = Σ` неоплачиваемых `BreakSegment` дня; `plannedUnpaid` = из плана дня;
  `effectiveUnpaidMs = recordedUnpaid > 0 ? recordedUnpaid : (grossDay ≥ порог ? plannedUnpaid : 0)`.
  Порог — 6 ч (финская норма; вынести в `CompanyAttendancePolicy` с дефолтом 360 мин).
- «Обед оплачивается» = в шаблоне дня `plannedBreakMinutes` трактуется как оплачиваемый
  (флаг `plannedBreakPaid` на `WorkScheduleTemplateVersionDay` — **1 миграция, 1 колонка**) ⇒
  `plannedUnpaid = 0`, а `plannedPaidBreak` собирается отдельно для отображения.
- Формула — DAY-level, поэтому меняется сигнатура `computeSegmentMs` → `computeDayMs(segments[], plannedUnpaidBreakMs, thresholdMs)`; все вызывающие (overview, reports, export, period totals) обновить.
- Экспорт (PDF/CSV): колонки `Unpaid brk` / `Worked` уже есть — просто станут корректными;
  добавить строку-пояснение «−30 мин обед (не оплачивается)» при авто-вычете.
- Задним числом: только новые расчёты (отчёт/экспорт считают на лету) — сохранённые версии не
  мигрируем. 11 черновиков пилота пересчитаются при первом просмотре отчёта.

**Открытые вопросы:** порог (6 ч vs без порога); «обед оплачивается» — на шаблон или на объект.
Оценка: 1–1.5 дня.

## E — надбавка за переработку (per day, только админ)

**Решения владельца:**
- Не стандартный случай, ставит **только админ** (работник не видит и не выставляет).
- **Под каждым днём** в табеле — контрол «переработка»: сколько часов и какой % (+50 % / +100 % / +200 %).
- % умножает часы. Должно быть в экспорте и **явно подсвечено** (красным), когда надбавка включена.
- Не усложнять: НЕ полный движок TES, просто ручная надбавка на день.

**Предлагаемая реализация:**
- Новая таблица **`TimesheetDayOvertime`** (или JSON-поле на `TimesheetDay`) — **1 миграция**:
  `timesheetVersionId`, `date`, `hours` (Decimal), `percent` (Int: 50/100/200), `note?`,
  `addedByUserId`, timestamps. Immutable как остальное содержимое версии (замораживается вместе с
  версией; правится через ту же correction-механику A).
- Контрол на карточке табеля / в `CorrectionDayEditor` (только для админа): «+ Надбавка» → часы + %.
- Расчёт: чистый (не в `worked-time.ts` — там только минуты). Отдельный `lib/reporting/overtime.ts`:
  `surchargeUnits = hours × percent / 100` (в «эквивалентных часах» доплаты). Экспорт получает
  доп. колонки: `OT hours`, `OT %`, `OT pay-equiv`. Красная подсветка строки в PDF при `OT > 0`.
- НЕ трогает `worked` (обычные часы) — надбавка идёт отдельной величиной поверх.
- Права: `timesheet.overtime.manage` — ADMIN/SUPER_ADMIN (**seed в той же миграции**).

**Открытые вопросы:** дневная или недельная база (пример владельца «9–10 ч +50 %, 11–12 ч +100 %» —
дневная, но вводит вручную, так что движок не нужен); хранить как эквивалент-часы или как деньги
(деньги = ставки = вне текущего scope, оставляем часы×%).
Оценка: 3–5 дней (миграция + расчёт + UI + колонки экспорта).
