# Titanor Time — FAQ для начальника / директора

Статус документа: рабочее руководство для ролей `ADMIN` и `SUPER_ADMIN`.

Интерфейс приложения сейчас в основном англоязычный, поэтому в руководстве рядом с русским
названием указаны реальные названия разделов и кнопок. Полная локализация интерфейса на английский,
русский и финский языки будет выполняться отдельным этапом.

## 1. Для кого это руководство?

Руководство предназначено для владельца компании, директора, начальника или офис-менеджера,
который отвечает за работников, объекты, табели и отчётность.

- `ADMIN` выполняет всю ежедневную операционную работу.
- `SUPER_ADMIN` может делать всё то же самое и дополнительно является техническим владельцем
  системы.
- Для обычной ежедневной работы рекомендуется использовать `ADMIN`, а `SUPER_ADMIN` оставлять для
  аварийных и системных действий.

## 2. С чего начать после первого входа?

Откройте раздел `Setup`. Рекомендуемый порядок первоначальной настройки:

1. Создайте объект в `Sites`.
2. В карточке объекта создайте хотя бы одну рабочую зону (`Work area`).
3. Установите геозону объекта (`Geofence`).
4. Создайте шаблон рабочей недели в `Templates`.
5. Создайте работника в `Workers`.
6. Создайте назначение работника на объект в `Assignments`.
7. При желании назначьте уполномоченного проверяющего объекта (`FOREMAN`). Этот шаг необязателен.
8. Создайте открытый расчётный период в `Periods`.
9. Только после назначения и открытия периода выдайте работнику код активации.

Город (`City`) является необязательным справочным полем. Отсутствие города не блокирует создание
объекта и работу системы.

## 3. Что находится в главном меню ADMIN?

| Раздел | Назначение |
|---|---|
| `Overview` | Общая оперативная картина по компании |
| `Setup` | Чек-лист первоначальной настройки |
| `Workers` | Работники, редактирование, активация и деактивация |
| `Users` | Системные пользователи и прорабы |
| `Sites` | Объекты, зоны, геозоны и назначенные прорабы |
| `Templates` | Шаблоны рабочих недель |
| `Assignments` | Назначения работников на объекты |
| `Periods` | Расчётные периоды и их участники |
| `Timesheets` | Табели работников |
| `Reports` | Отчёты по работнику, объекту и периоду |
| `Review` | Административная проверка частей табеля |
| `Corrections` | Исправления уже утверждённых табелей |
| `Exports` | Создание, история и скачивание CSV-экспортов |
| `Attendance exceptions` | Ошибки Check In/Out и спорные случаи |
| `Attendance policy` | Настройки автоматической отправки табелей |

## 4. Как создать работника?

1. Откройте `Workers`.
2. Нажмите `Create worker` или `Add worker`.
3. Заполните имя, фамилию, номер работника и контактные данные.
4. Сохраните запись.

Создание работника ещё не даёт ему возможность войти. Сначала необходимо:

- назначить работника на действующий объект;
- создать или открыть расчётный период, в котором он является участником;
- после этого сгенерировать код активации в карточке работника.

Если на странице списка временно отсутствует кнопка создания, прямой адрес формы:
`/admin/workers/new`. Этот навигационный недостаток включён в аудит T9.

## 5. Почему после создания работника он ещё не может войти?

Аккаунт работника создаётся в состоянии ожидания активации. Это сделано намеренно, чтобы работник
не вошёл в пустой аккаунт без объекта и периода.

Перед выдачей кода проверьте:

1. У работника есть активное назначение (`Assignment`).
2. Назначение действует на текущую дату.
3. Существует открытый период (`OPEN`).
4. Работник включён в этот период.

После этого сгенерируйте одноразовый код активации. Работник откроет ссылку или введёт код и задаст
собственный пароль.

## 6. Как отредактировать работника?

1. Откройте `Workers`.
2. Выберите нужного работника.
3. Измените доступные персональные данные.
4. Сохраните изменения.

Редактирование защищено номером версии записи. Если другой администратор успел изменить того же
работника, приложение не должно молча перезаписать его данные, а попросит обновить страницу.

Исторические часы, события и утверждённые табели при редактировании работника не изменяются.

## 7. Как удалить работника?

Физического удаления работников нет. Используйте `Deactivate worker`.

Это правильное поведение для системы рабочего времени: старый работник может присутствовать в
табелях, отчётах, CSV-экспортах и журнале аудита. Удаление его строки разрушило бы историю.

При деактивации:

- трудовые отношения становятся неактивными;
- вход пользователя отключается или переводится в процесс завершения;
- исторические данные сохраняются;
- старые отчёты продолжают работать.

Отдельно завершите его действующее назначение в `Assignments`, чтобы работник больше не числился на
объекте. Интерфейс завершения назначения дорабатывается в рамках T9; серверный механизм уже
существует.

## 8. Как создать объект?

1. Откройте `Sites`.
2. Нажмите `Create site` или `Add site`.
3. Укажите название и доступные адресные данные.
4. При необходимости выберите город.
5. Сохраните объект.

После создания откройте карточку объекта и настройте:

- рабочие зоны;
- геозону;
- назначенных прорабов;
- работников через раздел `Assignments`.

Если в списке временно нет кнопки создания, прямой адрес: `/admin/sites/new`. Этот недостаток также
включён в аудит T9.

## 9. Как закрыть старый объект?

Не удаляйте объект. Откройте его редактирование и снимите флаг `Active`.

Закрытый объект:

- остаётся в исторических табелях и отчётах;
- не должен предлагаться для новых обычных назначений;
- сохраняет старые геозоны, рабочие зоны и часы.

## 10. Что такое Work area?

`Work area` — зона внутри объекта, например:

- главный корпус;
- склад;
- второй этаж;
- двор;
- конкретный участок стройки.

В карточке объекта можно создать несколько зон, переименовать их, деактивировать и снова
активировать. Удаление не используется, потому что зона может присутствовать в истории табелей.

## 11. Как настроить GPS-геозону?

В карточке объекта откройте секцию `Geofence` и укажите:

- широту;
- долготу;
- допустимый радиус в метрах.

Каждое изменение создаёт новую версию. Предыдущая версия не редактируется и не удаляется. Благодаря
этому можно определить, какая геозона действовала в момент конкретного Check In.

До сохранения проверьте координаты и радиус. Слишком маленький радиус может отклонять реальных
работников из-за обычной погрешности GPS.

## 12. Как создать шаблон рабочей недели?

1. Откройте `Templates`.
2. Нажмите `Create template`.
3. Задайте рабочие дни, плановое начало, окончание и перерывы.
4. Сохраните шаблон.

Изменение существующего шаблона создаёт новую неизменяемую версию. Уже начавшееся назначение
продолжает использовать закреплённую за ним версию. Чтобы поменять график начавшегося назначения,
нужно корректно завершить или разделить назначение и создать новую его часть.

## 13. Как назначить работника на объект?

1. Откройте `Assignments`.
2. Нажмите `Create assignment`.
3. Выберите работника.
4. Выберите объект и, если требуется, рабочую зону.
5. Выберите версию шаблона недели.
6. Укажите даты действия.
7. При необходимости сделайте назначение основным (`Primary`).

Работник сможет выбирать в Check In и ручном timetable только объекты из своих действующих
назначений. Произвольный объект свободным текстом сейчас не поддерживается.

Если назначение уже началось, его объект, зона и шаблон не переписываются задним числом. Используйте
завершение или разделение назначения.

## 14. Как убрать работника с объекта, не удаляя историю?

Завершите `SiteAssignment`:

1. Откройте `Assignments`.
2. Найдите действующее назначение.
3. Выберите действие `End`.
4. Укажите дату окончания.
5. Если назначение заканчивается раньше запланированного, укажите причину.

После окончания работник перестаёт считаться назначенным на объект, но его старые часы и отчёты
сохраняются.

## 15. Обязательно ли назначать прораба?

Нет. ADMIN видит часы всех работников и может самостоятельно:

- открыть SITE-часть табеля в `Review`;
- вернуть её работнику с причиной;
- подтвердить её;
- после подтверждения всех частей выполнить final approval.

Отсутствие аккаунта или назначения FOREMAN не должно блокировать путь табеля от `SUBMITTED` до
`FINAL_APPROVED`.

Внутренний технический статус после подтверждения всех частей пока называется
`FOREMAN_APPROVED`. Это историческое имя enum; по бизнес-смыслу оно означает «проверка завершена,
готово к финальному утверждению» и не доказывает, что действие выполнил прораб.

В Titanor Time роль `FOREMAN` означает не должность человека в фирме, а уполномоченного
проверяющего по конкретным объектам. Такой пользователь является дополнительным помощником ADMIN,
а не обязательным звеном процесса.

## 16. Как создать или назначить уполномоченного проверяющего объекта?

Откройте `Users` и создайте прораба одним из способов:

- `Standalone` — отдельный пользователь, который сам не ведёт рабочие часы;
- `Existing employee` — существующий работник получает дополнительную роль `FOREMAN`.

После активации пользователя откройте карточку объекта и назначьте прораба с датой начала и,
при необходимости, датой окончания.

Проверяющий видит только назначенные ему объекты. Если он одновременно является работником, он не
может утверждать собственный табель.

Если человек не хочет регистрироваться в приложении, просто не назначайте его: ADMIN выполнит
проверку самостоятельно. Возможность подтверждения через временную защищённую ссылку может быть
добавлена позднее отдельным этапом; сейчас такой ссылки нет.

Создание и деактивация системных `ADMIN`/`SUPER_ADMIN`, свободное редактирование логина и полное
управление ролями пока не имеют законченного интерфейса. Это известное ограничение, а не скрытая
кнопка.

## 17. Как создать расчётный период?

1. Откройте `Periods`.
2. Создайте новый период и задайте даты начала и окончания.
3. Проверьте список участников.
4. Убедитесь, что работники, от которых ожидается табель, отмечены как `expected`.

Основные состояния периода:

- `OPEN` — работники заполняют и отправляют табели;
- `LOCKED` — период закрыт для обычных изменений и готовится к экспорту;
- `EXPORTED` — по периоду создан полный экспорт.

Период нельзя безопасно удалить, поскольку с ним связаны табели, версии и экспортные пакеты.

## 18. Что смотреть каждый день в Overview?

Начинайте рабочий день с `Overview`. Обратите внимание на:

- работников, которые отмечены сейчас;
- слишком долго открытые смены;
- пропущенные Check Out;
- GPS-исключения;
- ошибки offline-синхронизации;
- отправленные и возвращённые табели;
- открытые Attendance Exceptions;
- блокировки финального утверждения;
- разницу между recorded и reported временем.

Карточки состояний используются как фильтры. Нажатие на состояние показывает соответствующих
работников.

## 19. Что означают recorded и reported time?

- `Recorded` — время, полученное из Check In/Check Out и материализированных clock-смен.
- `Reported` — время, которое находится в текущем табеле или его утверждённой версии.
- `Diff` — разница между ними.

Разница не всегда означает нарушение. Работник мог исправить забытый Check Out, перерыв или рабочую
зону. Но значительное расхождение должно иметь понятную причину и пройти проверку.

Оплачиваемый перерыв входит в рабочее время. Из worked time вычитается только неоплачиваемый
перерыв.

## 20. Как проходит утверждение табеля?

Обычный процесс:

1. Работник отправляет табель — статус `SUBMITTED`.
2. Табель делится на области проверки по объектам.
3. ADMIN подтверждает область объекта или возвращает её с причиной. Если на объект назначен
   `FOREMAN`, эту SITE-область вместо ADMIN может проверить он.
4. После подтверждения всех необходимых областей статус становится `FOREMAN_APPROVED` — это
   техническое имя состояния «review завершён», а не обязательная подпись прораба.
5. ADMIN выполняет финальную проверку.
6. Табель получает статус `FINAL_APPROVED`.

Основной гарантированный путь всегда проходит через административную очередь `Review`. FOREMAN
только помогает с назначенными ему объектами и не является обязательным для работы компании.

## 21. Почему я не могу финально утвердить табель?

Откройте табель и проверьте причины блокировки. Возможные причины:

- не все review scopes подтверждены;
- осталось открытое Attendance Exception;
- смена работника ещё открыта;
- существует конфликт offline-событий;
- ожидается решение по Correction Request;
- данные изменились после отправки;
- нарушена последовательность состояний.

Не обходите блокировку прямым изменением данных. Сначала устраните указанную причину.

## 22. Что делать, если ADMIN или проверяющий вернул табель?

Работник увидит причину возврата. Табель снова станет редактируемым в статусе `RETURNED`.

Работник должен:

1. открыть соответствующий период;
2. исправить день или часы;
3. снова проверить итог;
4. отправить новую версию.

Старая отправленная версия остаётся в истории и не переписывается.

## 23. Что делать с Attendance Exception?

Откройте `Attendance exceptions`, затем карточку конкретного исключения. В зависимости от ситуации
можно:

- подтвердить просмотр;
- отклонить исключение;
- связать отдельные Check In и Check Out;
- подтвердить исходное назначение;
- принудительно закрыть зависшую смену;
- выполнить контролируемое исправление сегмента с обязательной причиной.

Всегда изучайте время, объект, работника и связанный табель. Исходные ClockEvent не удаляются и не
переписываются — исправление создаёт отдельный проверяемый след.

## 24. Как исправить уже окончательно утверждённый табель?

Не редактируйте `FINAL_APPROVED` напрямую. Используйте `Corrections`:

1. Создайте Correction Request и укажите причину.
2. Откройте correction draft.
3. Внесите необходимые изменения.
4. Отправьте запрос на решение.
5. Уполномоченный пользователь принимает или отклоняет его.
6. При принятии создаётся новая неизменяемая версия табеля.

Если период уже экспортирован, подходящее исправление попадёт в следующий `CORRECTION`-экспорт.

## 25. Какие отчёты доступны?

В `Reports` доступны три представления:

- `By worker` — часы выбранного работника по объектам;
- `By site` — работники и часы выбранного объекта;
- `By period` — итог по компании и строки объектов за период.

Отчёты используют один и тот же канонический источник:

- для `DRAFT` и `RETURNED` — текущий редактируемый draft;
- для отправленных и утверждённых состояний — неизменяемую текущую версию.

Поэтому отчёт не должен смешивать старую утверждённую версию с новым возвращённым draft.

## 26. Как создать CSV-экспорт?

1. Убедитесь, что нужный период заблокирован и все ожидаемые табели финально утверждены.
2. Откройте `Exports`.
3. Выберите период.
4. Создайте `FULL` export.
5. После создания проверьте количество строк, размер и хеш.
6. Скачайте файл обычной ссылкой `Download`.

После исправлений экспортированного периода создаётся `CORRECTION` export. Это полный новый снимок,
заменяющий предыдущий, а не список математических разниц.

CSV хранится в системе точными неизменяемыми байтами. Повторное нажатие или потеря сетевого ответа
не должны создавать дубликат.

PDF, зарплатные суммы, ставки и TES-категории пока не входят в экспорт.

## 27. Что настраивается в Attendance policy?

В `Attendance policy` ADMIN задаёт правила автоматической отправки табелей после окончания периода:

- количество дней ожидания;
- время запуска;
- задержку после повторного открытия;
- связанные параметры scheduler.

Scheduler не заменяет ежедневный контроль. Он является страховкой, если работник не отправил
табель вручную. Незакрытая смена при автоматической отправке создаёт исключение для проверки.

## 28. Что нельзя удалять и почему?

Titanor Time использует завершение жизненного цикла вместо физического удаления:

| Сущность | Правильное действие |
|---|---|
| Работник | `Deactivate worker` |
| Объект | снять `Active`, то есть закрыть объект |
| Рабочая зона | `Deactivate` |
| Назначение работника | `End assignment` |
| Назначение прораба | `End` |
| Шаблон | создать новую версию |
| Геозона | создать новую версию |
| Период | `Lock`, затем `Export` |
| Финальный табель | `Correction Request` |

Так сохраняется юридически и операционно важная история.

## 29. Что делать при сообщении Access denied?

Проверьте:

1. Под каким пользователем выполнен вход.
2. Есть ли у него роль `ADMIN` или `SUPER_ADMIN`.
3. Не была ли роль отозвана.
4. Не закончился ли срок действия роли.

Перезагрузка страницы не должна возвращать отозванное право: permissions проверяются сервером при
каждом запросе.

## 30. Что делать при сообщении Setup incomplete?

Обычно отсутствует один из обязательных элементов:

- активное назначение работника;
- открытый расчётный период;
- участие работника в периоде.

Вернитесь в `Setup`, откройте соответствующие разделы и завершите настройку. После этого повторите
генерацию кода активации.

## 31. Что делать при конфликте версии или Stale state?

Это означает, что данные уже изменил другой администратор, прораб, работник или scheduler.

1. Не повторяйте действие много раз подряд.
2. Обновите страницу.
3. Проверьте текущее состояние.
4. Повторите действие только если оно всё ещё необходимо.

Такая ошибка защищает систему от потери более свежих данных.

## 32. Что делать, если приложение кажется медленным?

До завершения отдельного performance-аудита:

- не открывайте множество тяжёлых отчётов одновременно в нескольких вкладках;
- используйте фильтры по периоду и объекту;
- уменьшите `pageSize` для больших списков;
- после мутации дождитесь завершения индикатора;
- зафиксируйте адрес страницы, действие и примерное время ожидания для T9-аудита.

Не выполняйте повторные двойные нажатия: приложение имеет защиту, но они затрудняют диагностику.

## 33. Какие проверки начальнику выполнять регулярно?

### Каждый день

- проверить `Overview`;
- проверить открытые смены и пропущенные Check Out;
- разобрать критические Attendance Exceptions;
- убедиться, что offline-события работников синхронизируются.

### Каждую неделю

- проверить новые и завершившиеся назначения;
- проверить общую очередь `Review` и, если используются FOREMAN, их очереди;
- проверить возвращённые табели;
- посмотреть отчёты по объектам и работников с крупным diff.

### В конце расчётного периода

- убедиться, что все ожидаемые работники отправили табели;
- проверить подтверждение всех SITE и NON_SITE scopes;
- закрыть исключения;
- выполнить final approval;
- заблокировать период;
- создать и скачать FULL CSV export;
- сохранить контрольный хеш экспортного файла.

## 34. Какие функции пока отсутствуют?

На текущем этапе не считаются завершёнными:

- полная локализация всего приложения на английский, русский и финский;
- полноценное управление ADMIN/SUPER_ADMIN и всеми ролями через UI;
- подтверждение часов внешним проверяющим через временную защищённую ссылку без регистрации;
- редактирование логина и email системного пользователя;
- физическое удаление исторических сущностей;
- свободный ввод неизвестного объекта работником;
- законченный процесс отпусков и больничных через UI;
- PDF-экспорт;
- расчёт зарплаты, ставок, overtime, night/Sunday/holiday и TES;
- финальный redesign и performance-аудит;
- приёмочные проверки на физических iPhone и Android.

## 35. Как сообщить об ошибке разработчику?

Для воспроизводимого отчёта укажите:

1. роль пользователя (`ADMIN`, `FOREMAN` или `WORKER`);
2. адрес страницы;
3. что было сделано до ошибки;
4. ожидаемый результат;
5. фактический результат;
6. точный текст ошибки;
7. дату и приблизительное время;
8. объект, период и работника без передачи пароля;
9. снимок экрана, если на нём нет секретов и лишних персональных данных.

Никогда не отправляйте разработчику пароль, session cookie, полный activation token или сырые GPS-
координаты.

## 36. Короткая памятка полного процесса

```text
Создать объект и рабочие зоны
→ настроить геозону
→ создать шаблон недели
→ создать работника
→ назначить работника на объект
→ открыть период
→ активировать аккаунт работника
→ работник ведёт Check In/Out и timetable
→ работник отправляет табель
→ ADMIN подтверждает или возвращает SITE/NON_SITE-части
  (назначенный FOREMAN при желании может проверить SITE-часть)
→ ADMIN выполняет final approval
→ ADMIN блокирует период
→ ADMIN создаёт FULL CSV export
→ поздние изменения проходят через Correction Request
→ ADMIN создаёт CORRECTION export
```
