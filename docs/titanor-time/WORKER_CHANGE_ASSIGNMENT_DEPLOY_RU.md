## Что добавлено

### Кнопка «Изменить объект / зону» у каждого текущего назначения (рядом с «Завершить»)
Два режима на выбор:
- **«Сменить только рабочую зону»** — тот же объект, с сегодня, одно поле «Рабочая зона»
  (+ «без зоны»). Один клик.
- **«Перевести на другой объект / зону»** — объект + рабочая зона + шаблон графика + дата (сегодня
  или будущее) + галочка «Основное назначение».

### Endpoint `POST /api/admin/assignments/:id/change`
Одна транзакция:
1. Черновые плановые смены **этого** назначения на даты `>= effectiveFrom` удаляются
   (пересоздаются для нового назначения на шаге 3).
2. Текущее назначение закрывается днём раньше даты перевода (`validTo = effectiveFrom − 1`).
   Запись **не удаляется** — ставится `validTo` + `endedReason` + `AuditEvent ASSIGNMENT_CHANGED`.
3. Новое назначение создаётся через `createAssignmentInTx` (тот же код, что `createAssignment` —
   участник периода, черновик табеля, плановые смены на новый объект/зону на остаток открытого
   периода).
- **Заднее число запрещено** (`< сегодня` → 400).
- **Сданный табель** или **уже отмеченные часы** на дату `>= effectiveFrom` → чистый **409**
  (`ASSIGNMENT_HAS_SUBMITTED_TIME` / `ASSIGNMENT_HAS_RECORDED_TIME`), не 500. Владелец: такие дни
  правятся в табеле при утверждении.
- «Пустой» перевод (тот же объект/зона/график) → 400 `NOTHING_TO_CHANGE`.
- Привязки GPS не тронуты (геозона на `WorkSite`, не на назначении).

### Открытая смена → выбор
Если у работника идёт чек-ин и дата перевода — сегодня, endpoint отдаёт **409
`OPEN_SHIFT_CHOICE_REQUIRED`**, и карточка спрашивает:
- **«Сегодня доработает на текущем объекте — перевод с завтра»** (`KEEP_ON_OLD`): дата перевода
  сдвигается на завтра, сегодняшняя смена целиком на старом объекте.
- **«Перенести и сегодня — вся смена на новый объект»** (`MOVE_TO_NEW`): `EmployeeOpenShift`
  (объект + зона + назначение) переезжает на новый объект; часы не прерываются, сегодняшний день
  числится за новым объектом. Чек-ин остаётся в журнале как факт («нажал вход на объекте A»).
Часы не прерываются ни в одном варианте.

### Карточка работника
- «Прошлые назначения» — свёрнутый блок (назначения с `validTo` в прошлом, до 20, новые сверху).
- `CurrentAssignment` теперь несёт `templateId`/`templateName` (предзаполнение формы).

## Инцидент при live-проверке (и его устранение)

- **Что:** первичная live-проверка включала «безопасный» пробный `POST …/change`, который я
  считал заведомо no-op'ом. Тело пробы **не содержало `templateId`**, поэтому endpoint увидел это
  как «убрать шаблон» — реальное изменение — и выполнил его с `effectiveFrom: 2099-01-01`.
- **Эффект на проде:** у Nazar Druz назначение `3d95975f` (Meyer Turku Shipyard, основное)
  получило `validTo = 2098-12-31` вместо `null` + `endedReason`; появилось фантомное назначение
  `3532e82c` с `validFrom 2099-01-01` без шаблона. **Влияния на работника нет** — фантом с датой
  2099 не «текущий» (невидим в карточке, в отметках, в отчётах), а старое назначение перекрывало
  «сейчас». Зона Aros Marine (`c6825d98`) не затронута. 14 плановых смен `3d95975f` не затронуты
  (дата пробы 2099).
- **Устранение (одна транзакция, с разрешения владельца, ~7 минут спустя):** физически удалено
  фантомное `3532e82c` (0 зависимостей, проверено); `3d95975f` возвращено к `validTo = NULL`,
  `endedReason = NULL`; добавлена компенсирующая запись `ASSIGNMENT_CHANGE_REVERTED` в аудит.
  Иммутабельные записи `ASSIGNMENT_CHANGED` (10:20) и `ASSIGNMENT_CHANGE_REVERTED` (10:27)
  остаются в журнале как честный след.
- **Вывод / на будущее:** live-проверка нового write-endpoint'а на проде должна быть строго
  read-only, либо использовать запрос, который гарантированно отклоняется **до** транзакции
  (битый UUID, отсутствующее обязательное поле). «no-op по бизнес-смыслу» не годится — набор
  полей, определяющих no-op, легко занизить.
- **Сам код `worker-change-bee072d` — не при чём:** endpoint отработал ровно по контракту
  (частичное тело = частичное изменение). Тесты CH0–CH10 это и проверяют.
