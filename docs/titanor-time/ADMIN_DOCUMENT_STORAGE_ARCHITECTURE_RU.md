# Titanor Time — архитектура закрытого раздела документов

Статус: **проект архитектуры, без реализации и без изменений production**
Дата: **2026-09-10**
Первая категория: **«Договоры»**
Логический лимит раздела: **10 ГиБ = 10 737 418 240 байт**
Основное файловое хранилище: **Contabo Object Storage, тариф 500 ГБ**

## 1. Цель первого этапа

В административной части Titanor Time нужен закрытый раздел для файлов. На первом этапе в нём
есть категория «Договоры». Пользователи с административными правами могут:

- видеть список документов и их версии;
- загружать новый документ;
- скачивать документ;
- заменять документ новой версией;
- удалять документ;
- видеть занятое и доступное место относительно лимита 10 ГиБ.

Архитектура должна позволять позднее добавить категории, например «Инструкции», «Шаблоны» или
«Сертификаты», без новой подсистемы хранения.

## 2. Что уже есть и переиспользуется

Titanor Time уже умеет работать с закрытыми файлами работников через `/app/uploads`, но новый
раздел документов не должен занимать локальный диск VPS. Владелец подтвердил, что его рабочее
место — купленное **Contabo Object Storage на 500 ГБ**.

На VPS это Object Storage исторически смонтировано как:

```text
/mnt/250gb
```

Название mount осталось от прежней конфигурации и не означает текущий размер. `df` показывает
для него фиктивные `4.0G` из-за особенностей `s3fs`; фактические 500 ГБ подтверждаются тарифом в
панели Contabo.

Docker не должен получать FUSE bind mount `/mnt/250gb`: для этой конфигурации такой bind уже
оказался ненадёжным. Приложение обращается к тому же хранилищу напрямую через приватный S3 API.
Основной namespace нового раздела:

```text
<Contabo bucket>/titanor-time-foundation/admin-documents/
```

Лимит 10 ГиБ — прикладная квота внутри общего Object Storage на 500 ГБ. S3 не резервирует
физический непрерывный раздел на 10 ГиБ: Titanor Time не разрешает объектам этого namespace
превысить `10 737 418 240` байт.

## 3. Границы доступа

Для первой версии вводятся независимые permission:

| Permission | Назначение | Начальные держатели |
|---|---|---|
| `document.read.all` | список, метаданные, скачивание, квота | `ADMIN`, `SUPER_ADMIN` |
| `document.upload` | создание документа | `ADMIN`, `SUPER_ADMIN` |
| `document.replace` | загрузка новой версии | `ADMIN`, `SUPER_ADMIN` |
| `document.delete` | перемещение документа в корзину | `ADMIN`, `SUPER_ADMIN` |
| `document.purge` | окончательное удаление из корзины | `SUPER_ADMIN` |

В текущей матрице роль `ADMIN` соответствует начальнику/офис-менеджеру. Доступ роли `FOREMAN`
не включается до подтверждения владельцем: прораб сейчас ограничен назначенными объектами, а
категория «Договоры» не имеет объектной области видимости.

Проверка permission выполняется на каждом API-запросе. Ссылка на файл не является разрешением:
по ней нельзя скачать документ без активной сессии и нужного permission.

## 4. Модель данных

Рекомендуется универсальная модель из четырёх сущностей.

### `DocumentCategory`

- `id` UUID;
- `code` — стабильный уникальный код, первая запись `CONTRACTS`;
- `nameRu`, `nameEn`, `nameFi`;
- `quotaBytes` — для `CONTRACTS` равно `10737418240`;
- `isActive`;
- `createdAt`, `updatedAt`.

### `AdminDocument`

- `id` UUID;
- `categoryId`;
- `title`;
- `description` nullable;
- `status`: `ACTIVE` или `TRASHED`;
- `currentVersionId`;
- `createdByUserId`, `createdAt`, `updatedAt`;
- `trashedByUserId`, `trashedAt` nullable;
- `version` для optimistic locking.

### `AdminDocumentVersion`

- `id` UUID;
- `documentId`;
- `versionNumber`, уникальный внутри документа;
- `storageKey` — путь, сгенерированный сервером;
- `originalFileName` — только отображаемое имя;
- `mimeType`, `sizeBytes`, `sha256`;
- `status`: `RESERVED`, `QUARANTINED`, `AVAILABLE`, `FAILED`, `PURGED`;
- `uploadedByUserId`, `createdAt`, `availableAt` nullable.

Версии неизменяемы. Замена создаёт следующую версию, затем атомарно меняет
`AdminDocument.currentVersionId`. Это сохраняет доказуемую историю и исключает момент, когда
старый файл уже удалён, а новый ещё не записан.

### `DocumentStorageUsage`

Одна строка на категорию:

- `categoryId` PK/FK;
- `usedBytes` — физически сохранённые доступные и старые версии;
- `reservedBytes` — место, зарезервированное незавершёнными загрузками;
- `updatedAt`.

Условие квоты:

```text
usedBytes + reservedBytes + newFileBytes <= quotaBytes
```

Изменение usage выполняется в транзакции с блокировкой строки категории. Поэтому две
одновременные загрузки не смогут вместе превысить 10 ГиБ. Периодическая сверка сравнивает БД с
реальными файлами и сообщает о расхождении, но не молча исправляет его.

В квоту входят текущие версии, предыдущие версии и файлы в корзине, пока они физически не
удалены. Временный файл учитывается через `reservedBytes`. Это не позволяет освободить квоту
только сменой статуса в интерфейсе.

## 5. Размещение файлов в Contabo 500 ГБ

Основной рабочий namespace в закрытом Contabo Object Storage:

```text
titanor-time-foundation/admin-documents/
```

Предлагаемая структура:

```text
titanor-time-foundation/admin-documents/
  objects/contracts/<document-uuid>/<version-uuid>.bin
  quarantine/<upload-uuid>.bin
```

Клиентское имя никогда не используется как S3 key. `storageKey` создаёт сервер из известного
category code и UUID, затем дополнительно проверяет обязательный префикс
`titanor-time-foundation/admin-documents/`.

Namespace не получает public bucket policy и не открывается через Caddy или `/public`. S3
credential приложения имеет доступ только к необходимому закрытому префиксу. Все операции
инициирует авторизованный API Titanor Time; постоянной копии документа на локальном диске нет.

## 6. Загрузка и замена

1. API проверяет сессию, CSRF, permission, category и размер multipart-запроса.
2. По размеру файла в транзакции создаётся reservation. При нехватке квоты возвращается
   `409 STORAGE_QUOTA_EXCEEDED` с `quotaBytes`, `usedBytes`, `reservedBytes`, `availableBytes`.
3. API потоково передаёт файл в закрытый `quarantine/` через S3 multipart upload. Весь файл не
   держится в памяти и не сохраняется постоянно на локальном диске VPS.
4. Во время потока вычисляется SHA-256 и проверяется фактический размер. Незавершённый multipart
   upload обязательно отменяется при ошибке и периодически очищается lifecycle-правилом.
5. Тип проверяется по содержимому (magic bytes), а не только по расширению и присланному MIME.
6. При необходимости файл проходит антивирусную проверку в quarantine.
7. После успешной проверки объект копируется сервером из quarantine в конечный S3 key, затем
   quarantine-объект удаляется. Метаданные не указывают на конечный объект до подтверждённого
   `HEAD` с ожидаемыми размером и checksum.
8. В транзакции версия становится `AVAILABLE`, reservation переносится в `usedBytes`, создаётся
   `AuditEvent`. Для замены переключается `currentVersionId`.
9. При любой ошибке quarantine/multipart-объект удаляется, reservation освобождается. Фоновая
   задача чистит зависшие reservation и orphan-объекты после безопасного TTL.

Мутации используют существующие правила Titanor Time: `X-Requested-With: titanor-time`,
`Idempotency-Key`, request ID и audit в той же транзакции, где меняются метаданные.

## 7. Удаление

Обычное удаление переводит документ в `TRASHED`, фиксирует пользователя, время и `AuditEvent`.
Файл остаётся закрытым и продолжает занимать квоту. По умолчанию предлагается хранить корзину
30 дней, затем отдельная задача окончательно удаляет версии и уменьшает `usedBytes`.

Немедленное окончательное удаление доступно только через `document.purge` и требует отдельного
подтверждения в UI. Срок корзины и необходимость восстановления надо подтвердить после получения
полного задания.

## 8. Скачивание

Маршрут скачивания перед выдачей файла повторно проверяет:

- активную сессию и `document.read.all`;
- статус документа и версии;
- размер и SHA-256 файла;
- соответствие пути разрешённому корню.

Ответ содержит:

```text
Content-Disposition: attachment
Cache-Control: private, no-store
X-Content-Type-Options: nosniff
Content-Length: <recorded size>
X-Content-SHA256: <recorded hash>
```

Безопасное имя в `Content-Disposition` формируется существующим helper Titanor Time.

## 9. API первого этапа

| Метод и путь | Действие |
|---|---|
| `GET /api/admin/documents/storage` | квота: занято, зарезервировано, доступно, процент |
| `GET /api/admin/document-categories` | доступные категории |
| `GET /api/admin/documents?category=CONTRACTS` | список и фильтры |
| `POST /api/admin/documents` | новый документ + первая версия |
| `GET /api/admin/documents/:documentId` | карточка и история версий |
| `GET /api/admin/documents/:documentId/download` | текущая версия |
| `GET /api/admin/documents/:documentId/versions/:versionId/download` | выбранная версия |
| `POST /api/admin/documents/:documentId/versions` | заменить новой версией |
| `DELETE /api/admin/documents/:documentId` | переместить в корзину |
| `POST /api/admin/documents/:documentId/restore` | восстановить из корзины |
| `DELETE /api/admin/documents/:documentId/purge` | окончательно удалить |

Списки имеют серверную пагинацию. Некорректный и недоступный UUID возвращает одинаковый 404 без
утечки существования файла.

## 10. Экран администратора

Новый пункт меню: **«Документы»**. Внутри первая плитка/вкладка: **«Договоры»**.

В верхней части всегда виден индикатор:

```text
Использовано 2,4 ГиБ из 10 ГиБ · Свободно 7,6 ГиБ · 24%
```

В `used` входят версии и корзина. Рядом показывается подсказка, сколько занимает корзина.

Таблица содержит название, категорию, текущую версию, размер, автора загрузки и дату. Действия:
«Скачать», «Заменить», «Удалить». Для `SUPER_ADMIN` в корзине дополнительно доступно
«Удалить окончательно».

Интерфейс не считает квоту на клиенте: после каждой мутации он получает актуальные значения от
сервера.

## 11. Типы и ограничения файлов

Точный allowlist определится после завтрашнего задания. Без явного решения загрузка произвольных
исполняемых файлов не допускается. Безопасный стартовый вариант:

- PDF;
- DOCX;
- XLSX;
- JPEG и PNG;
- до 100 МиБ на один файл.

Для ZIP, подписанных контейнеров, сканов TIFF и других форматов требуется отдельное решение.
Расширение, MIME и сигнатура должны согласовываться. HTML/SVG и исполняемые форматы по умолчанию
запрещены.

## 12. Backup и восстановление

Существующий `uploads.tar.gz` не является источником документов нового раздела: основные байты
живут непосредственно в Contabo Object Storage на 500 ГБ. PostgreSQL backup сохраняет всю
структуру, метаданные, версии, S3 keys, размеры и SHA-256.

До включения раздела в production для namespace документов нужно настроить:

- S3 versioning или эквивалентную защиту от случайного удаления;
- lifecycle для незавершённых multipart uploads и удалённых версий;
- manifest: количество файлов, суммарный размер и SHA-256;
- регулярную сверку manifest с объектами через `HEAD`;
- проверку восстановления файла по случайной выборке;
- понятный retention.

Копия в другом префиксе того же Object Storage не считается независимым backup: она не защищает
от потери аккаунта, региона или всего storage. Для полноценной второй копии впоследствии нужен
другой bucket/account/регион либо отдельный backup-провайдер. Это решение можно принять перед
production после уточнения ценности и срока хранения договоров.

Системные S3 versions и независимый backup не засчитываются в видимые пользователю 10 ГиБ.
Рабочие текущие версии, предыдущие версии приложения и корзина засчитываются.

## 13. Защита от заполнения хранилища

Логическая квота раздела не заменяет контроль общего Object Storage. Перед выдачей reservation
приложение проверяет свою квоту 10 ГиБ. Отдельный мониторинг отслеживает общую ёмкость тарифа
500 ГБ через S3/Contabo, а не через фиктивное значение `df` у `s3fs`.

Локальный диск VPS не используется для постоянных документов. Если библиотеке проверки
потребуется краткий временный файл, его размер ограничивается размером одной загрузки, каталогом
с отдельной локальной квотой и гарантированной очисткой. Предпочтителен полностью потоковый путь.

Отдельные сигналы мониторинга:

- категория занята на 80%, 90%, 95%;
- весь Contabo Object Storage приблизился к лимиту тарифа;
- локальный временный каталог приблизился к своему малому техническому лимиту;
- зависшая reservation;
- отсутствующий, лишний или повреждённый S3 object;
- ошибка S3 versioning/backup или restore-check.

## 14. Audit

Минимальные события:

- `ADMIN_DOCUMENT_CREATED`;
- `ADMIN_DOCUMENT_VERSION_UPLOADED`;
- `ADMIN_DOCUMENT_REPLACED`;
- `ADMIN_DOCUMENT_TRASHED`;
- `ADMIN_DOCUMENT_RESTORED`;
- `ADMIN_DOCUMENT_PURGED`;
- `ADMIN_DOCUMENT_DOWNLOAD_INTEGRITY_FAILED`.

В audit сохраняются UUID, версия, размер, MIME и SHA-256. Содержимое документа, путь на VPS и
секреты туда не попадают. Нужно отдельно решить, журналировать ли каждое успешное скачивание:
для договоров это полезно, но может заметно увеличить AuditEvent.

## 16. Что уточнить завтра

3. Если `FOREMAN` получает доступ, ко всем документам или только к документам его объектов?
4. Какие форматы и максимальный размер одного файла требуются?
5. Нужны ли название, номер договора, контрагент, дата, срок действия, объект и теги?
6. Нужен ли поиск по содержимому PDF/DOCX или только по метаданным?
7. Нужно ли хранить старые версии и сколько времени?

9. Нужна ли запись каждого скачивания в audit?
10. Должны ли документы быть связаны с работником, объектом, заказчиком или оставаться общими?
11. Должны ли 10 ГиБ относиться только к «Договорам» или ко всему разделу «Документы»?
12. Требуется ли антивирус до публикации файла пользователям?

## 17. Что намеренно не сделано сегодня

- не создан S3-префикс и не загружены объекты;
- не изменена БД и не применены миграции;
- не изменены роли и permissions;
- не изменены S3 credentials, bucket policy и mount points;
- не изменён backup;
- не перезапущены контейнеры.

Это оставляет production без изменений до получения точного задания и позволяет реализовать
подтверждённый вариант одним последовательным релизом.
